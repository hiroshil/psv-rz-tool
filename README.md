# RZ Vita VWF patcher

This package contains the RZ/Re:Zero Vita EBOOT VWF runtime patcher and the LT atlas helper used by the current localization workflow.

The current ownership model is:

- `lt_build_helper.py` updates an extracted LT project: `lt-atlas.png`, `lt-font.json.glyph_count`, and generated `font-widths.json`.
- `rz_vwf_stock_patcher.py` patches EBOOT runtime behavior: VWF hooks, runtime glyph limit, speaker/nameplate VWF, speaker pixel limit, and the runtime width table.
- `rz-tool build lt` builds `lt.bin` and owns LT allocation/load-size/sector-count updates in EBOOT.
- `rz-tool build sc` builds `sc.cpk` and owns SC allocation/script-buffer updates in EBOOT.

The patcher is not a byte-diff patcher. It assembles Thumb hook code with `keystone-engine`, derives the font profile from `font.tbl`, compiles a direct per-glyph runtime advance table, and writes only patch sites justified in the accompanying analysis documents.

## Recommended width workflow

For new font-rendered LT projects, use the generated JSON width table:

```text
lt-project/font-widths.json
```

`build_lt.py` emits this file from the exact font assignment used to rasterize each glyph. Use the same file for:

- `rz_vwf_stock_patcher.py --width-table`
- `rz-tool build sc --wrap-width-table`

This avoids divergence between runtime rendering and build-time wrapping.

### Why no width-table compression is used

The runtime helper already uses direct byte lookup:

```text
width = width_table[glyph_id - 0x0E12]
```

The number of distinct width values does not affect runtime table size. The bundled profile has 229 custom glyphs, so the runtime table is 229 bytes. The stock EBOOT cave at `0x8112B070` has `0x818` bytes available, enough for about 2072 custom glyphs. Compression would save little for the current profile and would make the hot glyph-render path more complex.

## Width artifacts

### `font-widths.json` - recommended

Generated by `build_lt.py`:

```bash
python tools/build_lt.py --i lt-project
```

or equivalently:

```bash
python tools/lt_build_helper.py --i lt-project
```

The JSON contains one integer advance per mapped glyph. Widths are derived from `ImageFont.getlength()` for the exact TTF/OTF that covers each character, rounded to integer pixels and clamped to `1..24` for the 24x24 LT cell profile.

### `font.cnf` - optional tuning/legacy format

`font.cnf` remains supported as a manual override/tuning format. Its intended role is now narrower:

```text
explicit font.cnf/JSON override
    > font metric from the selected TTF/OTF
    > [default] fallback only when a mapped glyph is preserved but cannot be measured
```

A bundled historical `examples/font.cnf` is retained for parity/reproduction. It is not silently applied to new font-rendered projects in a way that would suppress generated font metrics.

## What `vwf_patcher` owns

`rz_vwf_stock_patcher.py` owns EBOOT changes required for runtime VWF rendering:

- expanded glyph/runtime acceptance limits;
- mixed stock/custom VWF renderer hook at `FUN_8104E37E`;
- fixed-column/wrap guard hook at `FUN_8104E240`;
- speaker/nameplate advance hook at `0x8104DF0C -> 0x8110B110`;
- speaker/nameplate VWF length filter at `0x8104E02E -> 0x8110BF84`;
- runtime width table at `0x8112B070`;
- runtime glyph-limit sites derived from `font.tbl` capacity.

`vwf_patcher` does **not** own LT archive allocation.

## What `vwf_patcher` does not own

The patcher does not:

- build or repack `lt.bin`;
- patch LT load-size/sector-allocation constants (`0x8101B510`, `0x81129E5C`, `0x81129E60`);
- build or repack `sc.cpk`;
- patch SC sector/allocation tables;
- generate translation text;
- guess glyph widths without a width artifact or font metrics;
- expose manual runtime glyph-limit/probe flags.

LT allocation belongs to `rz-tool build lt`. SC allocation belongs to `rz-tool build sc`.

## Required files

```text

ENGINE_ANALYSIS.md
PROFILE_FORMULA_PROOF.md

examples/font.cnf

```

`font.tbl` maps glyph IDs to Unicode characters. The expanded visible/custom range starts at the stock engine limit `0x0E12`. The patcher reads every mapping at or above `0x0E12`, finds the highest custom glyph ID, and derives:

```text
glyph_range_start         = 0x0E12
glyph_range_end_exclusive = max_custom_glyph_id + 1
runtime_glyph_limit       = align_up(glyph_range_end_exclusive, 0x40) + 0x40
```

`glyph_range_end_exclusive` controls VWF helper range checks and width-table length. `runtime_glyph_limit` is the engine capacity ceiling patched into runtime bounds and intentionally includes one 0x40-glyph guard bucket after the last occupied bucket.

Final `lt.bin` allocation is derived from the rebuilt binary by `rz-tool build lt`, not by this patcher.

## Standard workflow

### 1. Extract stock LT project

For stock `lt.bin`, no allocation map is needed:

```bash
rz-tool extract lt.bin lt-project
```

For re-extracting a modified `lt.bin`, first extract the LT allocation map from the matching patched EBOOT:

```bash
rz-tool extract-lt-alloc eboot_patched_lt.elf lt-allocation.json
rz-tool extract lt.bin lt-project --allocation-map lt-allocation.json
```

Do not use `extract-lt-alloc` on an EBOOT that has only been processed by the standalone VWF patcher but has not yet gone through `rz-tool build lt`; its runtime glyph limit may be expanded while LT allocation is still stock.

### 2. Update LT atlas and generate widths

```bash
python tools/build_lt.py \
  --i lt-project \
  --font-file Arial.ttf \
  --font-file fallback.ttf \
  --summary-out lt_project_update.json
```

`--font-file` may be repeated. The first font covering each mapped character wins.

If `--font-file` is omitted, the tool searches for nearby `Arial.ttf`.

The tool updates:

```text
lt-project/lt-atlas.png
lt-project/lt-font.json
lt-project/font-widths.json
```

It does **not** build `lt.bin`.

`font.tbl` is auto-resolved and is the authoritative glyph mapping/profile source. `font.cnf` is optional tuning/override metadata. If a mapped glyph is not covered by the configured fonts and the existing atlas cell is blank/new, the tool fails instead of silently emitting a missing glyph.

### 3. Patch EBOOT runtime VWF

```bash
PYTHONPATH=./pydeps python3 rz_vwf_stock_patcher.py \
  --eboot-in eboot.bin.elf.org \
  --eboot-out eboot_vwf.bin.elf \
  --font-tbl examples/font.tbl \
  --width-table lt-project/font-widths.json \
  --speaker-max-width 192 \
  --summary-out patcher_summary.json
```

The input must be the expected stock EBOOT:

```text
SHA256 f5233a9ed15bedab8893800701a176da07986952fb0fb9ce92b33519327e1825
```

The patcher uses guarded writes. If a stock instruction at a patch site does not match the expected bytes, it refuses to write rather than producing a mixed or partially patched ELF.

### 4. Build `lt.bin` and update LT allocation in EBOOT

```bash
rz-tool build lt-project lt.bin \
  --eboot-in eboot_vwf.bin.elf \
  --eboot-out eboot_vwf_lt.bin.elf
```

`rz-tool` will:

1. build `lt.bin`;
2. verify `lt-font.json.glyph_count` against the runtime glyph limit in EBOOT;
3. compute the required allocation from the rebuilt `lt.bin`;
4. patch LT allocation/load-size/sector-count into the output EBOOT.

For this first LT build from the standalone VWF-patched EBOOT, `-f` is normally not required.

If the input EBOOT was already modified inside the protected runtime hash range by a previous allocation build, use `-f` intentionally:

```bash
rz-tool build lt-project lt.bin \
  --eboot-in previous_patched_eboot.elf \
  --eboot-out eboot_vwf_lt.elf \
  -f
```

`-f` only bypasses `VWF_RUNTIME_HASH_RANGE_SHA256` mismatch. It does not bypass glyph-count, allocation, alignment, or ELF validation.

### 5. Extract and translate SC

For stock `sc.cpk`:

```bash
rz-tool extract sc.cpk sc-project \
  --charset-map examples/font.tbl
```

For re-extracting a rebuilt `sc.cpk`, first extract SC allocation from the matching EBOOT:

```bash
rz-tool extract-sc-alloc patched_eboot.elf sc-allocation.json
rz-tool extract sc.cpk sc-project \
  --charset-map examples/font.tbl \
  --allocation-map sc-allocation.json
```

Translate `sc-project/scenario-dialogue.json`, focusing on `text` and `speaker` fields.

### 6. Build SC and final EBOOT

Use the same `font.tbl` and generated `font-widths.json`:

```bash
rz-tool build sc-project sc_patched.cpk \
  --eboot-in eboot_vwf_lt.bin.elf \
  --eboot-out final_eboot.bin.elf \
  --charset-map examples/font.tbl \
  --wrap-width-table lt-project/font-widths.json \
  --wrap-mode word \
  --wrap-rows 3 \
  -f
```

In the normal LT -> SC workflow, `-f` is intentional because `rz-tool build lt` has already changed LT allocation inside the protected runtime hash range. If SC build is run directly on the EBOOT produced only by standalone `vwf_patcher`, and no allocation build has modified that range yet, `-f` can be omitted.

If wrapping creates continuation/marker metadata, keep the generated file next to the archive:

```text
sc_patched.cpk.rz-dialogue-meta.json
```

### 7. Package final EBOOT for PS Vita

```bash
vita-make-fself.exe -c final_eboot.bin.elf eboot.bin
```

Deploy this final `eboot.bin` together with the rebuilt assets.

## Speaker/nameplate VWF

Static analysis found a separate fixed-width speaker/nameplate path that is not covered by the `FUN_8104E37E` dialogue hook:

```text
FUN_8104E404 case 0xFFF0
    -> FUN_8104DF94
        -> FUN_8104DE8C
            0x8104DF0C: r1 = r6 + 0x18
```

The patcher replaces only the fixed `+0x18` advance at `0x8104DF0C` with a helper using `width_table[glyph - 0x0E12]` for custom glyphs, 24px for stock glyphs, and the original glyph-0 behavior.

The stock speaker path also has an 8-glyph copy cap in `FUN_8104DF94`. The patcher replaces that with a VWF pixel budget bounded by the stock speaker envelope:

```bash
--speaker-max-width 192
# alias: --speaker-max-width-px 192
```

Accepted range is `48..192`. The default is 192px.

Speaker patches are static-analysis validated and should still receive runtime visual validation on target text before being called stable for a release.

## Stable E37E renderer model

The stable VWF helper uses one pixel-cursor model for mixed stock/custom rendering:

```text
if glyph >= glyph_range_end_exclusive:
    branch to original stock continuation
elif glyph < 0x0E12:
    render through the pixel-cursor helper and advance by 24px
else:
    render through the pixel-cursor helper and advance by width_table[glyph - 0x0E12]
```

This fixes mixed lines where stock Japanese glyphs such as `ラム` follow VWF custom glyphs. Stock glyphs retain 24px advance, but they use the same pixel cursor as custom glyphs.

Runtime validation for this renderer model:

```text
Deploy A cursor-single: PASS
- ラム no longer appears blank at the expected position.
- ラム is no longer pushed to the row end after custom VWF glyphs.

Deploy B continuation: PASS
- No visible errors in the long continuation/wrap/fold-back test.
- The same renderer model remains valid under the current continuation sidecar workflow.
```

## Validation and re-extract checks

After building final assets:

```bash
python tools/validate_engine_assets.py \
  --elf final_eboot.bin.elf \
  --secrect secrect.json
```

`--secrect` is the spelling used by the current validator CLI.

Extract final allocation maps for archival/re-extract:

```bash
rz-tool extract-lt-alloc final_eboot.bin.elf lt-allocation.final.json
rz-tool extract-sc-alloc final_eboot.bin.elf sc-allocation.final.json
```

Recommended round-trip checks:

```bash
rz-tool extract lt.bin lt-reextract \
  --allocation-map lt-allocation.final.json

rz-tool extract sc_patched.cpk sc-reextract \
  --charset-map examples/font.tbl \
  --allocation-map sc-allocation.final.json
```

## Common failure cases

If custom glyphs render as 24px fixed-width, check that the patched EBOOT is deployed and that `--width-table` points to the `font-widths.json` generated for the current LT project.

If text wraps differently from runtime rendering, check that the exact same `font-widths.json` was used by both `rz_vwf_stock_patcher.py` and `rz-tool build sc --wrap-width-table`.

If some Vietnamese glyphs are blank in `lt-atlas.png`, verify that the selected `--font-file` list actually covers those Unicode codepoints. A file named `Arial.ttf` may not be Microsoft Arial; inspect the summary output for font family/version and missing glyphs.

If stock Japanese glyphs such as `ラム` appear blank at the expected position or appear later near the row end after VWF custom glyphs, verify that the stable mixed stock/custom E37E helper is deployed.

If SC edits crash but no VWF glyphs are involved, investigate `rz-tool` SC rebuild/allocation output rather than this patcher.

## Release contents policy

Kept because they are required or evidentiary:

- `examples/font.tbl`: default glyph mapping/profile input;
- `examples/font.cnf`: optional legacy/tuning width profile;
- `tools/build_lt.py` and `tools/lt_build_helper.py`: LT atlas project updater and `font-widths.json` generator;
- `PROFILE_FORMULA_PROOF.md`: bucket+guard profile proof;
- `ENGINE_ANALYSIS.md`: disassembly-backed patch-site contract;
- `evidence/*.json`: machine-readable summaries.

Excluded because they are generated outputs:

- patched EBOOT/LT/SC deployment files;
- Python `__pycache__`;
- stale per-step checksum manifests.

## Bundled default profile

For the bundled `examples/font.tbl`:

```text
glyph range:       0x0E12..0x0EF6
used end:          0x0EF7
runtime limit:     0x0F40
custom glyphs:     229
atlas glyph_count: 0x0F40
```

There is intentionally no public `--runtime-glyph-limit` flag. To add more glyph capacity, add glyph IDs to `font.tbl` and update the LT atlas project; runtime capacity moves to the next 0x40 bucket plus one guard bucket automatically.
